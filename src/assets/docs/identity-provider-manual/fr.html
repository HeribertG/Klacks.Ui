Manuel des fournisseurs d'identité

Introduction

Les fournisseurs d'identité permettent l'authentification des utilisateurs via des services d'annuaire externes tels que LDAP, Active Directory ou OAuth2/OpenID Connect.

Types de fournisseurs pris en charge:

  • LDAP - Lightweight Directory Access Protocol standard
  • Active Directory - Microsoft Active Directory
  • OAuth2 - Framework d'autorisation OAuth 2.0
  • OpenID Connect - Couche d'identité sur OAuth 2.0

Import de clients

Lorsque "Utiliser pour l'import de clients" est activé, les données suivantes sont importées:

  • Nom - sn (nom de famille) ou displayName
  • Prénom - givenName
  • Titre - title (titre professionnel)
  • Entreprise - company
  • Adresse - street/streetAddress, postalCode, l (ville), st (état), c (pays)
  • Genre - Depuis personalTitle (M./Mme) pour Active Directory

Note: Pour OpenLDAP, le genre est par défaut "Neutre" et peut être corrigé manuellement.

Connexion par l'annuaire

Lorsque « Utiliser pour l'authentification » est activé et enregistré, les personnes peuvent se connecter à Klacks avec leur mot de passe de l'annuaire. Personne n'obtient l'accès automatiquement : l'administrateur autorise chaque personne dans l'onglet Autorisation de connexion.

  • L'onglet liste les comptes de l'annuaire (1000 au maximum ; la recherche permet d'affiner la liste).
  • Cocher un compte crée un nouveau compte Klacks sans rôle ni mot de passe. Les comptes Klacks existants ne sont jamais repris : si l'adresse e-mail est déjà utilisée par un compte Klacks, la ligne ne peut pas être cochée. Supprimez d'abord ce compte ou modifiez son adresse e-mail dans la gestion des utilisateurs.
  • Décocher désactive le compte Klacks ; cocher à nouveau le réactive, tant qu'il n'a pas de rôle. Un compte désactivé qui possède encore des rôles se réactive dans la gestion des utilisateurs.
  • Départ : lorsqu'une personne quitte l'entreprise, décochez aussi son compte dans Klacks. Bloquer le compte dans l'annuaire empêche les nouvelles connexions, mais les sessions en cours continuent jusqu'à leur expiration.
  • Un compte sans adresse e-mail dans l'annuaire ne peut pas être autorisé.
  • Votre propre compte ne peut pas être modifié dans cet onglet.
  • Une personne dont les identifiants de l'annuaire sont corrects mais qui n'est pas autorisée reçoit le message que son compte n'est pas autorisé et qu'elle doit contacter l'administrateur.

Klacks recherche la personne avec l'utilisateur de liaison, puis vérifie le mot de passe auprès de l'annuaire ; l'identifiant n'a donc pas besoin de correspondre à l'adresse e-mail.

Chiffrement

LDAP simple sur le port 389 transmet les mots de passe en clair ; le formulaire affiche un avertissement pour un fournisseur LDAP sans SSL. Utilisez LDAPS (« Utiliser SSL », port 636) dès que l'annuaire sert à la connexion.

Active Directory : connexion uniquement via LDAPS

Klacks connecte les personnes à Active Directory uniquement via LDAPS (port 636). Sans SSL, le formulaire affiche un avertissement, personne ne peut se connecter et l'onglet Autorisation de connexion reste fermé. Sans SSL, l'import de clients et le test de connexion ne fonctionnent que si Klacks tourne directement sous Windows ; dans Docker (Linux), Active Directory exige LDAPS pour tout.

  • Hôte : le nom complet (FQDN) exactement tel qu'il figure dans le certificat du contrôleur de domaine, p. ex. dc01.example.local. Une adresse IP ne fonctionne pas, car la vérification du certificat compare le nom.
  • Faire confiance à l'autorité de certification : l'ordinateur qui exécute Klacks doit faire confiance à l'autorité qui a émis le certificat du contrôleur de domaine. Windows : importez le certificat de l'autorité dans le magasin Autorités de certification racines de confiance de l'ordinateur, p. ex. certutil -addstore Root ca.cer (en tant qu'administrateur).
  • Résolution de noms : si le FQDN n'est pas résolu par le DNS, ajoutez une entrée dans le fichier hosts (Windows : C:\Windows\System32\drivers\etc\hosts).
  • Docker : montez le certificat de l'autorité en fichier PEM dans le conteneur de l'API, définissez la variable d'environnement LDAPTLS_CACERT sur ce chemin et ajoutez le FQDN avec extra_hosts si le DNS ne le résout pas. Si le contrôleur de domaine n'envoie pas de certificat d'autorité (certificat auto-signé), son propre certificat en fichier PEM sert d'ancre de confiance. Sans certificat de confiance, la connexion est refusée et signalée comme erreur de connexion.
  • Compte de liaison : saisissez-le sous forme de nom d'utilisateur principal (UPN), p. ex. svc-klacks@example.local.

Comptes importés

  • Les comptes désactivés et les comptes système d'Active Directory ne sont jamais importés ni listés.
  • Excluez les comptes de service avec le filtre utilisateur, p. ex. uniquement les membres d'un groupe : (&(objectCategory=person)(objectClass=user)(memberOf=CN=Klacks,OU=Groups,DC=example,DC=local))

Conseils

Synology NAS comme serveur LDAP

Un NAS Synology peut être utilisé comme serveur LDAP. Installez le paquet « LDAP Server » ou un conteneur Docker avec OpenLDAP.

  • Type de fournisseur : « LDAP » (pas « Active Directory »)
  • Filtre utilisateur : (objectClass=inetOrgPerson)
  • Connexion avec l'uid ou l'adresse e-mail
  • Utilisez de préférence LDAPS (port 636)

Tester la connexion

Le bouton « Tester la connexion » permet de vérifier la configuration. Il affiche le nombre de comptes actifs trouvés par le filtre utilisateur (les comptes désactivés et système ne sont pas comptés) et quelques noms d'utilisateur d'exemple. Un « + » après le nombre signifie que le serveur d'annuaire s'est arrêté à sa limite de résultats ; il y a donc davantage de comptes.
