Identity Provider Manual

Introduction

Identity Providers enable user authentication through external directory services such as LDAP, Active Directory, or OAuth2/OpenID Connect.

Supported Provider Types:

  • LDAP - Standard Lightweight Directory Access Protocol
  • Active Directory - Microsoft Active Directory
  • OAuth2 - OAuth 2.0 Authorization Framework
  • OpenID Connect - Identity layer on top of OAuth 2.0

Client Import

When "Use for Client Import" is enabled, the following data is imported:

  • Name - sn (surname) or displayName
  • First Name - givenName
  • Title - title (job title)
  • Company - company
  • Address - street/streetAddress, postalCode, l (city), st (state), c (country)
  • Gender - From personalTitle (Mr/Mrs) for Active Directory

Note: For OpenLDAP, gender defaults to "Neutral" and can be manually corrected.

Sign-in through the directory

When "Use for Authentication" is enabled and saved, people can sign in to Klacks with their directory password. Nobody gets access automatically: the administrator approves each person on the Sign-in approval tab.

  • The tab lists the directory accounts (at most 1000; use the search to narrow the list).
  • Ticking an account creates a new Klacks account without a role and without a password. Existing Klacks accounts are never taken over: if the e-mail address is already used by a Klacks account, the row cannot be ticked. Delete that account or change its e-mail address in the user administration first.
  • Removing the tick deactivates the Klacks account; ticking again reactivates it, as long as it has no role. A deactivated account that still has roles is reactivated in the user administration.
  • Offboarding: when someone leaves, remove the tick in Klacks as well. Disabling the account in the directory blocks new sign-ins, but sessions that are already running continue until they expire.
  • An account without an e-mail address in the directory cannot be approved.
  • Your own account cannot be changed on this tab.
  • A person with correct directory credentials but without approval gets the message that the account is not approved and should contact the administrator.

Encryption

Plain LDAP on port 389 sends passwords unencrypted; the form shows a warning for an LDAP provider without SSL. Use LDAPS ("Use SSL", port 636) whenever the directory is used for sign-in.

Active Directory: sign-in only over LDAPS

Klacks signs people in to Active Directory only over LDAPS (port 636). Without SSL the form shows a warning, nobody can sign in and the sign-in approval tab stays closed. Without SSL, client import and the connection test work only when Klacks runs directly on Windows; in Docker (Linux) Active Directory needs LDAPS for everything.

  • Host: the fully qualified name (FQDN) exactly as it appears in the domain controller's certificate, e.g. dc01.example.local. An IP address does not work, because the certificate check compares the name.
  • Trust the CA: the computer that runs Klacks must trust the certificate authority that issued the domain controller certificate. Windows: import the CA certificate into the computer's Trusted Root Certification Authorities store, e.g. certutil -addstore Root ca.cer (as administrator).
  • Name resolution: if the FQDN cannot be resolved through DNS, add a hosts entry (Windows: C:\Windows\System32\drivers\etc\hosts).
  • Docker: mount the CA certificate as a PEM file into the API container, set the environment variable LDAPTLS_CACERT to its path, and add the FQDN with extra_hosts if DNS does not resolve it. If the domain controller does not send a CA certificate (self-signed certificate), its own certificate as a PEM file works as the trust anchor. Without a trusted certificate the connection is refused and reported as a connection error.
  • Bind account: enter it as user principal name (UPN), e.g. svc-klacks@example.local.

Which accounts are imported

  • Disabled accounts and Active Directory system accounts are never imported and never listed.
  • Exclude service accounts with the user filter, e.g. only members of one group: (&(objectCategory=person)(objectClass=user)(memberOf=CN=Klacks,OU=Groups,DC=example,DC=local))

Tips

Synology NAS as LDAP Server

A Synology NAS can be used as an LDAP server. Install the "LDAP Server" package or a Docker container with OpenLDAP.

  • Provider Type: "LDAP" (not "Active Directory")
  • User Filter: (objectClass=inetOrgPerson)
  • Users sign in with their uid or e-mail address
  • Prefer LDAPS (port 636)

Test Connection

Use the "Test Connection" button to verify the configuration. It shows the number of active accounts the user filter finds (disabled and system accounts are not counted) and some sample user names. A "+" after the number means the directory server stopped at its result limit, so there are more accounts.
