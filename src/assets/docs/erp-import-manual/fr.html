Importation des commandes ERP – Manuel

Qu'est-ce que l'importation des commandes ERP ?

Les systèmes ERP externes livrent leurs commandes à Klacks sous forme de fichiers XML. Trois canaux de transfert sont disponibles :

  • Drop point (collecte) : l'ERP dépose les fichiers dans l'espace de dépôt du drop point – selon l'installation, un répertoire sur le serveur Klacks (par défaut) ou un stockage d'objets compatible S3. Klacks collecte les fichiers automatiquement selon la planification configurée.
  • Téléversement direct (push) : l'ERP envoie le fichier par HTTP POST à /api/erp-import/upload en s'authentifiant avec un jeton d'importation ERP comme jeton Bearer. Chaque fichier est limité à 50 Mo.
  • Téléversement manuel : les administrateurs glissent les fichiers XML directement dans la zone de dépôt de cette page (ou cliquent sur la zone pour sélectionner un fichier). Après le téléversement, l'importation est déclenchée automatiquement et démarre dans la minute ; le bouton Importer maintenant permet de la relancer à tout moment.

Drop point

Le drop point est la boîte aux lettres centrale pour tous les fichiers d'importation. Klacks le gère automatiquement – personne ne doit le créer ni le configurer. La page affiche son contenu sous forme de vue de fichiers avec trois zones : Entrée (en attente de la prochaine exécution d'importation), Traités (archive) et Erreurs (fichiers illisibles ou invalides avec la cause de l'erreur). Les fichiers en erreur peuvent être replacés dans l'entrée via le bouton Réimporter.

  • Interrupteur actif (importation active) – met en pause l'importation automatique ; les fichiers déjà déposés sont conservés.
  • Affichage d'état – heure de la dernière interrogation et, le cas échéant, la dernière erreur.

Jetons d'accès

  • Les administrateurs peuvent créer des jetons d'accès pour la livraison en push — nécessaires uniquement si un système ERP externe livre des fichiers via HTTPS. Chaque jeton commence par le préfixe klacks_erp_.
  • La durée de validité est configurable (1 à 730 jours, 365 jours par défaut).
  • Le jeton en clair n'est affiché qu'une seule fois, à la création. Il ne peut plus être récupéré ensuite – il faut le copier immédiatement et le conserver en lieu sûr.
  • Un jeton d'importation ERP est délibérément valable uniquement pour le point de terminaison d'importation. En cas de fuite chez le prestataire ERP, aucun autre accès API à Klacks n'est possible avec ce jeton.
  • Les jetons peuvent être révoqués à tout moment ; l'accès cesse immédiatement.

Planification

La collecte du drop point suit une expression cron (par défaut 0 * * * * = toutes les heures) dans le fuseau horaire sélectionné. Les deux se configurent sur cette page. Une expression cron invalide arrêterait l'importation – la saisie est donc validée et les valeurs invalides ne sont pas enregistrées.

Format XML (référence)

L'élément racine est ErpOrderImport avec les attributs obligatoires schemaVersion (actuellement 1) et sourceSystemId. Le sourceSystemId identifie le système livreur dans les fichiers et assure l'affectation stable des clients à travers toutes les livraisons – il doit rester constant pour chaque système source. Chaque commande figure dans son propre élément <Order>. Un fichier peut contenir un nombre quelconque de commandes.

Élément Obligatoire Format Signification
ExternalOrderReference Oui Texte Référence de commande unique du système ERP.
Description Non Texte Texte libre de la commande (p. ex. consignes d'intervention) ; affiché sur la commande.
Customer Oui Élément Données client de la commande (voir sous-éléments).
Customer/ExternalCustomerReference Non (recommandé) Texte Référence client externe ; garantit une attribution stable du client à chaque importation.
Customer/Company Oui Texte Raison sociale du client.
Customer/Address/Street Oui Texte Rue et numéro.
Customer/Address/Zip Oui Texte Code postal.
Customer/Address/City, Customer/Address/State, Customer/Address/Country Non Texte Localité, canton/région et pays.
FromDate Oui yyyy-MM-dd Début de la commande.
UntilDate Non yyyy-MM-dd Fin de la commande ; absent ou vide = durée indéterminée.
StartTime, EndTime Oui HH:mm Heure de début et de fin de l'intervention.
IsTimeRange Non true/false (false par défaut) true = plage horaire dans laquelle le travail a lieu ; false = service fixe de StartTime à EndTime. Si true, Duration est obligatoire.
Duration Si IsTimeRange=true Élément avec <Hours> et <Minutes> (entiers) Durée de l'intervention, p. ex. 0 h 20 min pour une visite de 20 minutes dans la plage 08:00–15:00. Facultatif pour un service fixe ; en son absence, la durée de StartTime à EndTime s'applique.
Quantity Non Entier (1 par défaut) Nombre d'interventions.
SumEmployees Non Entier (1 par défaut) Nombre de collaborateurs requis.
Weekdays Oui Attributs monday … sunday, chacun true/false Jours de la semaine de la commande ; au moins un jour doit être true, un attribut absent vaut false. Les commandes sans jour de semaine sont rejetées.

Remarque : les noms d'éléments sont sensibles à la casse. Un fichier d'exemple complet est disponible via le bouton Télécharger le fichier d'exemple au-dessus de ce manuel.

Attribution des clients

Klacks attribue chaque commande à un client :

  • D'abord via la combinaison ID du système source + référence client externe – une fois attribuée, cette référence renvoie durablement au même client.
  • Sans référence externe, la première occurrence est recherchée via raison sociale + code postal + rue ; la casse et les espaces sont ignorés.
  • Sans correspondance, Klacks crée automatiquement le client.

Traitement & cycle de vie

  • Les commandes importées sont créées comme brouillons et doivent être vérifiées et scellées par les planificateurs ou les administrateurs. Lors de la vérification, le planificateur ajoute aussi les qualifications requises — l'ERP peut les transmettre comme indication dans le champ Description.
  • Si l'ERP livre plus tard une version modifiée d'une commande déjà scellée, Klacks clôt automatiquement l'ancienne commande par date de fin et crée une nouvelle version brouillon liée. Les interventions futures déjà planifiées et non verrouillées de l'ancienne commande sont supprimées et les planificateurs sont notifiés.
  • Les livraisons répétées inchangées (p. ex. un export complet nocturne) ne déclenchent rien.

Gestion des erreurs & archive

  • Les fichiers traités sont déplacés dans le sous-dossier processed/ de l'espace de dépôt (archive, pas de suppression) ; ils apparaissent sur la page d'importation dans la zone Traités.
  • Les fichiers illisibles ou invalides sont déplacés dans le sous-dossier error/ et apparaissent dans la zone Erreurs ; de là, ils peuvent être replacés dans l'entrée via Réimporter.
  • Les commandes incomplètes ou non valides sont rejetées (par exemple sans jour de semaine, avec UntilDate avant FromDate ou avec une ExternalOrderReference en double dans le même fichier) ; les autres commandes du même fichier sont tout de même importées.
  • Un fichier contenant au moins une commande rejetée passe dans la zone Erreur avec le motif du rejet — les commandes déjà importées restent importées.
  • Les erreurs sont journalisées et les administrateurs sont notifiés.
